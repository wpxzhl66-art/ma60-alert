# 无限制手机推送 · 开源方案调研报告

版本 v1.0.0 · 调研日期 2026-10-18 · 数据来源：GitHub 仓库/官方文档/第三方评测（检索当日核实）

---

## 一、背景与调研目标

当前工具用 Server酱（方糖）推送到手机，免费版限 5 条/天，A股预警、期货、形态、新闻共用额度。目标：在 GitHub 上找**可无限制推送**的开源方案，给出对比与推荐。

使用环境约束（影响选型）：
- 接收端是 **iPhone**（现有 Server酱推送在 iPhone 上接收）
- 网络在中国大陆（部分海外服务直连不稳）
- 发送端在 GitHub Actions 云端 + 本机 Windows（无长期开机的公网服务器）

## 三、逐项说明

### 1. Bark（github.com/Finb/bark + Finb/bark-server）★ 推荐

**原理**：iOS App 注册到苹果 APNs 拿到 device token，交给 bark-server 保存；发送端对一个 URL 发 HTTP GET/POST（`https://服务器/{device_key}/{标题}/{内容}`），bark-server 转发给 APNs，由苹果系统级推送到手机。App 本体不需要运行、不耗电、不怕杀后台。

- **无限制**：官方明确「正常请求（HTTP 200）无任何限制」；仅当 5 分钟内 >1000 次错误请求（400/404/500）才会 ban IP 24h。对本项目一天几条到几十条的量级完全无感。
- **两种用法**：① 直接用官方公共服务器 `api.day.app`（免费、无条数限制、零部署）；② 自建——单 Docker 容器（`finab/bark-server`，8080 端口，BBolt 内嵌库，可选 MySQL），以后可以无痛从公共服切到自建（App 里换服务器地址即可）。
- **iOS 体验**：原生系统推送，支持 critical alerts（可绕过勿扰）、自定义铃声、加密推送、时效性通知。
- **适用场景**：给 iPhone 推自定义通知；脚本/监控/CI 报警。
- **已知限制**：
  - 只支持 iOS，无安卓端（对本人无影响）。
  - 公共服务器上消息内容对服务器运营者可见（敏感内容可用加密推送或自建解决）。
  - 个别运营商 DNS 污染导致连不上 api.day.app（如江苏移动），官方提供同集群备用域名 api1.day.app 无缝切换。
  - 社区项目，无 SLA。
- **许可**：MIT（App 与服务端均开源）。

### 2. ntfy（github.com/binwiederhier/ntfy）

**原理**：topic 化的 pub/sub。发送端 `PUT/POST https://服务器/主题名`，所有订阅该主题的设备收到通知。自建单容器部署，支持 Android/iOS/Web/CLI/WebUI、附件、定时发送、Markdown、端到端加密。

- **无限制**：自建完全自主；公共服务 ntfy.sh 免费但有访客级速率限制，付费档解锁更多。
- **已知限制（关键）**：
  - **自建服务器的 iOS 即时推送依赖转发**：iPhone 后台不能长连接，官方方案是自建服务器把「拉取请求」转发给 ntfy.sh 中转——即自建了也得经过官方服务器才能让 iPhone 秒收，否则只能靠 App 轮询（延迟大、耗电）。
  - 作者自述 iOS App「bare bones、有点 buggy」，落后于安卓端。
  - ntfy.sh 在大陆的直连稳定性未验证（本次未实测，标为未知）。
- **许可**：Apache-2.0 + GPLv2 双许可。
- **适用场景**：多平台、需要附件/定时/WebUI/多订阅者的场景；是 Bark 的最强跨平台替代。

### 3. Gotify（github.com/gotify/server）

**原理**：REST API 进（按应用 token POST），WebSocket 出（客户端长连接收消息），带 WebUI、多用户、插件、OIDC。

- **无限制**：自建完全自主，~16k stars、发版规律（2026-09 出 v3.1.1）。
- **已知限制（对本场景是硬伤）**：**无官方 iOS App**。iPhone 锁屏后 WebSocket 断开，无法系统级推送，第三方 iOS 客户端不可靠。官方定位 Android + Web 优先。
- **许可**：README 声明 MIT（注意：仓库元数据标注 NOASSERTION，采用前以仓库内 LICENSE 文件为准）。
- **结论**：iPhone 用户不选。

### 4. message-pusher（github.com/songquanpeng/message-pusher）

**原理**：自建消息路由网关（Go 单文件 + WebUI），一个接口分发到邮件/微信测试号/QQ/企业微信/飞书/钉钉/Bark/Telegram/Discord/腾讯云短信等十余个通道，支持通道组、Server酱兼容 API。

- **定位辨析**：它是**路由聚合层**，不是推送通道本身——「无限制」取决于你接的下游通道（接 Bark 就无限制，接 Server酱仍 5 条/天）。
- **已知限制**：最后提交 2025-11，维护节奏放缓（但单文件 Go 程序，现状稳定可用）；官方域名 msgpusher.com 将于 2026-11-24 下线，需迁到 push.justsong.cn。
- **许可**：MIT。
- **适用场景**：想同时接多个推送渠道、做统一入口和多通道兜底时值得加一层；只解决「超 5 条」则不必引入。

### 5. PushDeer（github.com/easychen/pushdeer）❌ 不推荐

**原理**：与 Bark 同类（HTTP API → APNs），曾提供轻 App/iOS/安卓/Mac 多端。

- **关键事实**：README 顶部官方警告「**本项目已不再维护**，Android 版因接口权限停用，社区不活跃，建议改用持续维护的 Server酱³」。自架版服务端**推送证书需每年手动更新**，忘了更就静默失效。
- **许可**：GPLv2 且**禁止商用**。
- **结论**：淘汰。

### 6. 附注：Telegram Bot（非 GitHub 自托管项目，仅作对照）

免费无条数限制、API 极简、支持 Markdown/按钮。但大陆网络需要代理才能收发，依赖第三方 IM 在国内的可用性，作为推送主通道风险偏高。不列为正式候选。

## 四、对比结论

| 维度 | Bark | ntfy | Gotify | message-pusher | PushDeer |
|---|---|---|---|---|---|
| iPhone 秒收（系统级推送） | ✅ APNs 原生 | ⚠️ 自建需经官方中转 | ❌ | 间接 | ✅（项目停更） |
| 零部署起步（不买服务器） | ✅ 公共服免费 | ⚠️ 公共服有限速 | ❌ 需自建 | ❌ 需自建 | ✅ 官方服（停更中） |
| 条数限制 | 无 | 自建无/公共服有限速 | 无 | 看下游 | 无 |
| 大陆可达性 | 好（国产项目，有备用域名） | 未知（未实测） | — | 好（自建在内网/国内机） | — |
| 部署复杂度 | 一个容器、零配置 | 一个容器、可选配置 | 一个容器+反代注意 WebSocket | 一个容器 | 复杂（Laravel+证书年更） |
| 维护活跃度 | 活跃 | 非常活跃 | 活跃 | 放缓 | **停更** |
| 许可 | MIT | Apache-2.0/GPLv2 | MIT（以 LICENSE 文件为准） | MIT | GPLv2 非商用 |

## 五、推荐

**首选：Bark。**

选型依据（按本项目的实际约束逐条对上）：
1. **接收端是 iPhone** → Bark 是唯一「原生 APNs 秒收 + 不耗电 + 支持重要警报」的方案；ntfy 的 iOS 体验官方自认欠佳，Gotify 直接没有 iOS 客户端。
2. **想零部署起步** → 用官方公共服务器 `api.day.app` 就无限量免费，装个 App 复制一个 Key 即完成接入；日后想要完全自主，Docker 单容器切自建，App 端只改一个服务器地址。
3. **大陆网络** → 国产项目、为国内用户设计，官方备有抗 DNS 污染的备用域名。
4. **接入成本极低** → 推送就是一个 HTTP GET（`https://api.day.app/{key}/{标题}/{内容}`，支持 GET/POST 与 Markdown），在 `pusher.py` 旁边加一个 Bark 通道即可；建议做成 Server酱 + Bark 双通道：Server酱额度照用（5 条内的强提醒），超出额度或普通消息走 Bark，额度焦虑直接消失。
5. **许可宽松**（MIT）、项目活跃（最新版 2026-10-10）。

**备选：ntfy**——若日后有安卓设备/桌面端/多订阅者/附件需求，ntfy 是最完整的跨平台方案；届时 iOS 秒收需接受「自建服务器经 ntfy.sh 中转」或改用公共服务。

**不选**：Gotify（无 iOS）、PushDeer（停更 + 证书年更）、message-pusher（多一层聚合，但不解决通道本身的限制；维护放缓）。

## 六、落地提示（如决定接入 Bark）

- 手机装 App Store 的 Bark，打开 App 拿到形如 `https://api.day.app/xxxxxxxxx/` 的推送 URL（Key 即凭证，等同密码，注意保管）。
- 服务端改造点在 `src/alert/pusher.py`：新增 bark 通道函数（requests GET/POST），配置项加 `bark.url` 与 `bark.enabled`；`daily_limit` 护栏只对 Server酱通道生效，Bark 通道不占额度。
- 测试一条：浏览器打开 `https://api.day.app/{你的Key}/测试标题/测试内容` 即可验证。
- 内容含特殊字符时用 POST JSON（`{"device_key":..., "title":..., "body":...}`）而非 GET 拼接。
