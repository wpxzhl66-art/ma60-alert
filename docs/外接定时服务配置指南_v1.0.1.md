# 外接定时服务配置指南 v1.0.0

> 目的：让「60周线预警」在**本机（Windows）关机**时也能准点执行与推送。

## 一、为什么要外接一个定时服务

现状有三个调度源，各有各的问题：

| 调度源 | 准点性 | 关机后 | 说明 |
|---|---|---|---|
| GitHub 自带 cron | ❌ 实测延迟 8~9 小时 | ✅ 能跑 | 平台级故障，2026-10-15 全天 24 个网格触发点 **0 个准点到达** |
| 本机 WorkBuddy 定时任务 | ✅ 准点 | ❌ 全停 | 依赖电脑开机 + 客户端在线 |
| **外接定时服务（本指南）** | ✅ 准点 | ✅ 能跑 | 由外部服务器在准点调 GitHub API，再把活交给 GitHub Actions |

关键点：**真正的扫描工作是在 GitHub 的服务器上跑的**，外接服务只负责「准点敲一下门」。
所以电脑关机完全不影响——只要外接服务准点发出请求，GitHub 就会立刻开工。

---

## 二、总览：要做两件事

| 步骤 | 谁来做 | 大概耗时 |
|---|---|---|
| A. 创建 GitHub 细粒度令牌（PAT） | **你本人** | 3 分钟 |
| B. 注册 cron-job.org 并建 5 条定时任务 | **你本人** | 10 分钟 |

账号密码、短信验证码、服务条款勾选必须你本人完成，我不能代操作。

## 三、步骤 A：创建 GitHub 细粒度令牌

**为什么需要**：外接服务要用一个令牌代表你调用 GitHub API，触发仓库的 workflow。

### A1. 打开创建页面

https://github.com/settings/personal-access-tokens/new

### A2. 填写基本信息

| 字段 | 填什么 |
|---|---|
| Token name | `ma60-alert-cron`（名字随意） |
| Expiration | 建议 **1 年**（最长 366 天，到期后需重新生成） |
| Description | 外部定时服务触发预警 workflow |

### A3. Repository access（关键：最小权限）

选 **Only select repositories** → 只勾选 `wpxzhl66-art/ma60-alert`。
**不要**选 "All repositories"。

### A4. Permissions（关键：只给一项）

展开 **Repository permissions**，只设置：

| 权限 | 级别 |
|---|---|
| **Actions** | **Read and write** |
| 其它全部 | 保持 No access |

> ⚠️ 不要用「经典令牌（Classic token）」并勾 `repo` 全权限——那等于把整个仓库的读写权交给了外部服务。
> 细粒度令牌只授权这一个仓库的 Actions，即使泄漏，损失可控。

### A5. 生成并立即复制

点 **Generate token**，页面会显示一次 `github_pat_...`。
**离开页面后就再也看不到**，请立刻复制到安全的地方。

## 四、步骤 B：注册 cron-job.org 并建任务

cron-job.org 是完全免费的定时请求服务（免费账户最多 50 个任务、最小间隔 1 分钟），
社区里大量用它绕开 GitHub cron 的延迟问题。

### B1. 注册

https://cron-job.org/en/signup/ → 填邮箱 + 密码 → 收验证邮件点确认。

### B2. 设默认时区（重要）

登录后进入 **Settings**，把 **Timezone** 设为 **Asia/Shanghai**。
否则你填的 `09:35` 会被按 UTC 解释，实际在北京时间 17:35 触发。

### B3. 创建任务

进入 **Cronjobs → Create cronjob**，按下表逐条创建。
每条除「时间」「Body」不同外，其余字段都一样。

**所有 5 条任务共用的字段：**

| 字段 | 值 |
|---|---|
| Title | 见下表 |
| URL | `https://api.github.com/repos/wpxzhl66-art/ma60-alert/actions/workflows/alert.yml/dispatches` |
| Execution | **Enabled** |
| Request method | **POST** |
| Days of week | 只勾 **Monday ~ Friday**（周一至周五） |
| Request body | 见下表 |
| Headers | 三条，见下 |

**要添加的 3 个 Header：**

| Key | Value |
|---|---|
| `Accept` | `application/vnd.github+json` |
| `Authorization` | `Bearer github_pat_你的令牌` |
| `Content-Type` | `application/json` |

> `Bearer` 和令牌之间有一个空格。令牌换成步骤 A 复制的那串。
> 注意：**每条任务都要加这 3 个 Header**，cron-job.org 不会跨任务继承。

**5 条任务的时间与请求体：**

| # | Title | 时间（北京时间） | Request body |
|---|---|---|---|
| 1 | 预警 09:35 | 每天 **09:35** | `{"ref":"main","inputs":{"task":"scan"}}` |
| 2 | 预警 10:15 | 每天 **10:15** | `{"ref":"main","inputs":{"task":"scan"}}` |
| 3 | 预警 13:30 | 每天 **13:30** | `{"ref":"main","inputs":{"task":"scan"}}` |
| 4 | 预警 14:20 | 每天 **14:20** | `{"ref":"main","inputs":{"task":"scan"}}` |
| 5 | 预警收盘确认 15:10 | 每天 **15:10** | `{"ref":"main","inputs":{"task":"confirm"}}` |

> 时间在 cron-job.org 的 **Schedule** 区，用「Every day at HH:MM」这个模式。
>
> 这 5 条**每天都跑**：交易日走扫描，非交易日（周末/节假日）由交易日校验自动转成
> 财经要闻轮——同一时刻、同一轮次，每轮只推当日新增条目，无新增不推送。

### B4.（可选）开启失败告警

在 **Settings → Notifications** 里开启失败邮件通知。
外接服务调不通时会给你发邮件——这能让你第一时间发现令牌过期等问题。

## 五、验证配置是否生效

### 方法一：看 cron-job.org 的执行历史

每条任务都有 **History** 页，能看到最近的请求和 HTTP 状态码。

| 状态码 | 含义 | 处理 |
|---|---|---|
| **204** | ✅ 成功，GitHub 已接受 | 无需处理 |
| 401 | 令牌无效或已过期 | 重新生成 PAT，更新 5 条任务的 Header |
| 404 | 仓库 / workflow 名写错，或 PAT 没勾选该仓库 | 核对 URL 拼写与步骤 A3 |
| 422 | 请求体格式错 | 检查 JSON 是否完整，引号是否为英文半角 |

> 204 表示「GitHub 已收到指令」，不代表扫描已完成。扫描实际是否跑成，看下一条。

### 方法二：看 GitHub 的 Actions 运行记录

https://github.com/wpxzhl66-art/ma60-alert/actions

应该能看到 `workflow_dispatch` 触发的运行记录。
点进去看日志里是否出现 `[gate] 北京 HH:MM → 命中槽位 ...`。

### 方法三（最直接）：等一条推送

准点跑成时会收到微信/推送通知。配置好后当天若有触发标的，就能收到。

## 六、和本机定时任务的关系

代码里有一道**槽位闸门**（`.github/scripts/slot_gate.py`）：

- 每个槽位（09:35 / 10:15 / 13:30 / 14:20 / 15:10）**每天只跑一次**；
- 谁先到谁跑，后到的立即退出（幂等，不会重复扫描、不会重复推送）；
- 外接服务、本机定时任务、GitHub 自带 cron **三个调度源都过这道闸门**。

这意味着**本机任务和外接服务可以同时存在**，不会冲突，只是多一层冗余：

| 方案 | 效果 |
|---|---|
| 只留外接服务 | 关机也能跑；外接服务本身出问题时无人补位 |
| **两者都留（推荐）** | 外接服务当主力；本机在线时若它没跑成，本机补位 |

另外还有一道**迟补兜底**：

- 如果某个交易日**一次都没跑成**，那么当天任何更晚到达的触发都会补扫一次并推送；
- 这样即使外接服务也延迟了，只要当天有触发到达就不漏一整天。

### 形态板块也一起覆盖了

右侧反转形态的判定引擎只有一份，本机与云端都能跑（云端读仓库里的
`store/daily/` 分片仓，最近 400 个交易日，25MB）。云端那轮挂在
**收盘确认（15:10）** 上——所以第 5 条任务跑成，形态板块当天也就跑成了，
不需要额外加任务。

| 板块 | 本机（关机后） |
|---|---|
| A 股 MA60 预警 | ✅ 外接服务触发，云端跑 |
| 右侧反转形态 | ✅ 同上（15:10 收盘确认轮一并跑） |
| 期货加权指数 | ✅ 随 16:07 数据更新轮一起刷新（见下） |

### ⚠️ 唯一还留在 GitHub cron 上的：每日数据更新轮

16:07 那轮（`task=update`）负责把当天行情并进云端数据仓（`store/`），
它**只有 GitHub 自带 cron 在触发**，外接服务没接管。影响与对策：

- GitHub cron 目前**能派发、只是延迟**（8~9 小时）——延迟无害，
  当天数据总会在当晚入库，第二天开盘前一定就位；
- 万一 GitHub cron 再次**整体失效**（2026-08-26 曾连续几天完全不派发），
  云端数据仓会停止更新。本机有兜底：`daily_run.py` 会检查分片仓落后是否超过
  3 个交易日，超了就自动从本机全历史日线重新播种一次。
- 所以真正需要你留意的是：**本机如果连着好几天没开机，云端数据仓也可能变旧**。
  长期关机又想完全自动，可以再加第 6 条外接任务触发 `task=update`（需要先用
  一天一次的打标保护，避免重复跑重抓任务）——需要时告诉我，我来加。

### 手动补跑

闸门会在当天已跑过时挡住重复触发。要**强制补跑**，加一个 `force` 参数：

```bash
gh workflow run alert.yml -f task=scan -f force=true
```

> 外接服务的 5 条任务**不要**设 `force` —— 否则会绕过去重，和本机任务重复扫描。

## 七、后续维护

| 事项 | 说明 |
|---|---|
| 令牌到期（建议 1 年） | 到期前重新生成，更新 5 条任务的 `Authorization` Header |
| 令牌泄漏 | 立即到 GitHub 令牌页 **Revoke**，再生成新的 |
| 修改触发时间 | 改 cron-job.org 任务时间即可，代码不用动 |
| GitHub cron 恢复后 | 仓库里的 cron 定义**保留不动**——多一个调度源无害（闸门会去重） |
