## A. 调度链路

### 1.【高·已知待办】GitHub cron 平台延迟 8~9 小时，云端兜底实际无效
- 位置：`.github/workflows/alert.yml` 的 schedule 触发
- 现象：2026-08-26 起 GitHub 平台级故障，白天 24 个网格点 0 个准点到达；
  cron-job.org 外接定时服务尚未配置（需用户本人注册 + 创建细粒度 PAT）
- 影响：本机不开机 = 当天无扫描无推送（优雅降级已有：不会推过期数据）
- 建议：按 `docs/外接定时服务配置指南_v1.0.1.md` 配置 cron-job.org（用户本人操作）

### 2.【中】16:07 数据更新轮无「当日已更新」幂等保护
- 位置：`.github/workflows/alert.yml`「更新数据仓」步骤；`run_update_cloud()`
- 现象：同一交易日重复 dispatch 会重复跑全市场增量更新（约 1.5h 预算、
  5000+ 请求），有触发 baostock 黑名单的风险
- 触发条件：外接定时服务接管 16:07 任务后（cron-job.org 会与 GitHub cron 双触发）
- 建议：仿照 `slot_gate.py` 加「update 已打标」检查（扫描轮已有此机制，update 轮没有）

### 3.【低】交易日校验把任何非 0/42 退出码都当「非交易日」
- 位置：`alert.yml`「交易日校验」步骤：`python -m alert.run_alert --is-trading-day || echo skip=true`
- 现象：`--is-trading-day` 正常时退出 0（交易日）/ 42（非交易日）；
  但网络故障、行情接口异常等导致的**其他非零退出**也会落入 `||` 分支
- 影响：接口抖动当天全部扫描被静默跳过（表现为「今天怎么没扫」）
- 建议：改为显式判断退出码，仅 42 跳过，其余报错重试

### 4.【中】手动 force 补跑在 16:07 更新之后会复权因子错位
- 位置：`scanner.evaluate()`；快照 `hfq_last_close` 与行情 `preclose` 的日期配对
- 现象：正常生产流程中扫描时段（10:05–15:55）日线仓必然停在昨日（16:07 才更新），
  `factor = hfq_last_close / preclose` 两个量同日、配对正确。但若 16:07 更新后
  手动 `gh workflow run alert.yml -f task=scan -f force=true`，日线已含当日 →
  `hfq_last_close`（当日）与 `preclose`（昨收）错位一天 → dev 系统性偏差约当日涨跌幅
- 实测佐证：2026-10-16 凌晨复测（日线与行情同日的非常态）触发 20 只，
  而日线精确重算为 17 只，3 只为错位导致的假触发
- 建议：`evaluate()` 校验快照 `last_date` 与行情快照日期差是否恰为一个交易日，
  不一致则对该股用 `_verify_exdiv` 同款腾讯日线重算因子（或整轮拒绝并告警）

### 5.【低】workflow 条件依赖 `steps.gate.outputs.run` 的空值语义
- 位置：`alert.yml` 各步骤的 `if: steps.gate.outputs.run != 'false'`
- 现象：update / demo 轮闸门步骤被跳过 → 该输出为空 → `!= 'false'` 为真 →
  依赖安装与交易日校验照跑。行为正确但依赖「空字符串恰好不等于 'false'」，
  后续改动容易踩坑
- 建议：给闸门步骤加 `id` 并对未运行的轮显式输出 `run=na`，条件改判等

## B. 判定链路

### 6.【中】A 股扫描没有停牌冻结行情过滤
- 位置：`scanner.evaluate()` / `quoter.py`
- 现象：长期停牌股（腾讯源日线冻结、成交额 NaN，实测样例 sh.600825 已停牌 3 天
  且收盘价三连同值）的行情接口仍返回价量 > 0 的冻结数据；价格不动而 MA60 每周
  下移时，停牌股可能「被动上穿」→ 产生**无法交易的假触发**
- 对照：期货模块有 `RT_MAX_LAG_DAYS` 校验（按品种行情日期落后全市场剔除），
  A 股 quoter/scanner 没有等价机制
- 建议：`evaluate()` 剔除「行情 ts 日期落后全市场最新行情日 ≥ 2 天」的标的；
  另可在快照层排除 amount 连续多日 NaN 的标的

### 7.【中】快照缓存 3 天，数据修复后扫描最多滞后 3 天
- 位置：`ma60_base.load_snapshot(max_age_days=3)`
- 现象：本机扫描优先读缓存快照；某只股票的数据被修复后（如本轮双汇 10-15 23:11
  补齐），若 16:07 的 update 轮没有跑（电脑关机），次日扫描仍用旧快照判定
- 本轮实况：双汇修复后当天未重建快照 → 10-14 扫描用了坏 MA60（假触发的直接推手之一）
- 建议：`run_scan` 前检查 data/daily 最新日期与快照 last_date 是否一致，不一致强制重建；
  或 16:07 update 轮失败时发出显式告警（当前只影响次日数据新鲜度，无提示）

## C. 数据链路

### 8.【低】store 腾讯兜底标的无 hfq 日线分片
- 位置：`cloud_store.append_daily_shards(fetched)`（只写 baostock 抓到的）
- 现象：103+10 只腾讯源标的在 store/daily 分片仓中缺失 → 形态板块云端扫描
  覆盖不到它们（已知降级，memory 有载）
- 建议：如需覆盖，可用腾讯日线 hfq（仿射口径）单独建分片并在 pattern 判定层
  标注来源；代价是口径管理复杂化，建议维持现状仅作记录

### 9.【低】腾讯兜底标的的 last_date 语义与 baostock 标的不一致
- 位置：`cloud_store._tencent_one()`（last_date 取周线最后一根 = 含未完成周）
- 现象：腾讯标的的 last_date 是「抓取当天」而非「最后交易日」；极端时序下
  （如周一凌晨做修复）会让该股当轮增量更新被 todo 判定跳过一天
- 影响：最多晚一天更新，无数据错误；仅在手工修复类操作时出现
- 建议：`_tencent_one` 的 last_date 改取「未完成周前最后一根完整周线日期」；
  或在 update todo 判定里对腾讯源放宽一天

### 10.【低】基准文件 hs300.csv.gz 日常链路不更新
- 位置：`data/benchmark/hs300.csv.gz`（仅 `build_dataset.py` 建库时生成，实测停在 10-13）
- 现象：近一月库的交易日历已改为「基准 ∪ 本地日线并集」兜底（v1.11.1 已修），
  但**研究管线**（run_study.py 的相对沪深300 超额计算）仍读这份旧基准
- 建议：在 16:07 更新轮追加一步基准指数增量抓取（baostock 指数接口或腾讯），
  或在 run_study 读入时校验基准新鲜度并告警

### 11.【低】推送额度上限硬编码
- 位置：`dashboard/build.py` 的 `"limit": 5`
- 现象：Server酱免费额度若变更，看板额度条与实际配额不一致（config 里无对应字段）
- 建议：额度写入 config/alert_config.yaml 并由此读取

## D. 展示层

### 12.【低】推送文案与看板标签命名不一致
- 位置：`template.py risk_level()`（推送「放量追高/缩量温和」）
  vs `app.js riskLevel()`（看板「涨得猛/跌得慢」）
- 现象：同一分档概念两种叫法（v1.11.0 界面白话化的遗留）；阈值两侧一致，无数据问题
- 建议：二选一统一。若统一为白话，推送文案相应改动即可

### 13.【低】趋势流水混入本机测试扫描
- 位置：`store/state/history.json`（扫描流水）；`build_data()` 的 trend
- 现象：2026-10-14 16:31–16:37 的三轮本机测试扫描（当时已收盘）被记为
  「盘中扫描」并计入趋势图；测试扫描与生产扫描共用一条流水，无法区分
- 建议：`run_scan` / `run_prepare` 加环境标记（如 `ALERT_TEST=1` 时跳过
  `_record_dashboard_state`），或流水条目加 `manual` 字段供前端过滤

### 14.【低】云端 append 模式下「当日跌回线下」状态失真
- 位置：`dashboard/history.py from_latest()`（`"above": True` 硬编码）
- 现象：本机重算模式（rebuild）不受影响（优先级更高）；仅云端 append 模式下，
  盘中触发的股票若收盘跌回 60 周线下方，历史页「仍站上」计数会短暂虚高
- 建议：`from_latest` 的 state 用最新行情价与快照 ma60_prev 复算 above，
  或接受该误差（次日重算即修正）

### 15.【低】`fut_alert._fmt` 数字格式化逻辑绕
- 位置：`fut_alert.py:102-104`
- 现象：三段式小数位选择写成一行的条件表达式，可读性差（功能正确）
- 建议：拆成普通 if/return（纯可维护性，无行为影响）

### 16.【低】`run_scan` 本地 confirm 空触发也推送的设计依赖推送开关
- 位置：`run_alert.run_scan()` 的 `elif push and mode == "confirm"` 分支
- 现象：收盘确认批「每次必推」（无触发也推一条报平安）；推送关闭时
  `pusher.send` 返回 False 已正确拦截，但若未来恢复推送，空报平安消息
  也会消耗额度（每日 5 条中占 1 条）
- 建议：可考虑「收盘确认仅在当日尚无任何推送时才发报平安」，省额度；
  或维持现状（用户可能想要确定性回执）
